### 1. No rate limiting on any public endpoint

**Files:** `artifacts/api-server/src/routes/bookings.ts`, `quotes.ts`, `reviews.ts`, `openai.ts`

**Problem:** `POST /api/bookings`, `POST /api/quotes`, `POST /api/reviews`, and the entire OpenAI conversation chain have zero rate limiting. A bot can flood your inbox, accumulate OpenAI API costs, and fill the database with junk in minutes.

**Fix:**
```bash
npm i express-rate-limit
```

```typescript
// Add to artifacts/api-server/src/app.ts
import rateLimit from 'express-rate-limit';

const formLimiter = rateLimit({
  windowMs: 60 * 1000,   // 1 minute
  max: 5,                // 5 requests per minute per IP
  message: { error: 'Too many requests, please try again later.' }
});

const aiLimiter = rateLimit({
  windowMs: 60 * 60 * 1000, // 1 hour
  max: 20,                   // 20 AI conversations per hour per IP
});

// Mount before router
app.use('/api/bookings', formLimiter);
app.use('/api/quotes', formLimiter);
app.use('/api/reviews', formLimiter);
app.use('/api/openai', aiLimiter);
```

### 2. Silent email and SMS failures — you will never know they failed

**Files:** `bookings.ts` (sendBookingEmails), `quotes.ts` (sendQuoteEmails), `lib/sms.ts`

**Problem:** All three helpers catch every error with an empty `catch {}` block. If SMTP is misconfigured or Twilio credentials are wrong, customers receive no confirmation, the business gets no alert, and nothing appears in logs. This is invisible data loss.

**Fix:**
```typescript
// BEFORE (in bookings.ts, quotes.ts, sms.ts)
} catch {}

// AFTER — add logging in every catch block
} catch (err) {
  logger.error({ err }, 'Failed to send email notification');
}

// For sms.ts
} catch (err) {
  logger.error({ err }, 'Failed to send SMS notification');
}
```

### 4. OpenAI route errors bypass the global error handler

**File:** `artifacts/api-server/src/routes/openai.ts`

**Problem:** `openai.ts` handles errors inline by writing to the SSE stream instead of calling `next(err)`. OpenAI failures are invisible to the global error handler and pino logger — extremely hard to debug in production.

**Fix:**
```typescript
// In SSE message handler catch block — log before writing error to stream
} catch (err) {
  logger.error({ err }, 'OpenAI stream error');
  res.write(`data: ${JSON.stringify({ error: 'Stream error' })}\n\n`);
  res.end();
}
```

### 5. Admin login has no brute-force protection

**File:** `artifacts/api-server/src/routes/admin-login.ts`

**Problem:** `POST /api/admin/login` uses plain string equality with no rate limiting, no attempt counter, and no account lockout. A script can attempt unlimited password guesses.

**Fix:**
```typescript
// Add to app.ts before router mount
const loginLimiter = rateLimit({
  windowMs: 15 * 60 * 1000, // 15 minutes
  max: 5,                    // 5 attempts
  message: { error: 'Too many login attempts. Try again in 15 minutes.' }
});
app.use('/api/admin/login', loginLimiter);
```

### 6. Session cookie missing `secure: true` at Express level

**File:** `artifacts/api-server/src/app.ts`

**Problem:** Session cookie sets `httpOnly` and `sameSite: 'lax'` but not `secure: true`. If the Replit proxy ever misconfigures HTTPS, the session cookie could be sent over HTTP.

**Fix:**
```typescript
// In app.ts session config — change this:
cookie: {
  httpOnly: true,
  sameSite: 'lax',
  maxAge: 7 * 24 * 60 * 60 * 1000
}

// To this:
cookie: {
  httpOnly: true,
  sameSite: 'lax',
  secure: process.env.NODE_ENV === 'production',
  maxAge: 7 * 24 * 60 * 60 * 1000
}
```

### 7. PATCH endpoints missing Zod validation

**Files:** `artifacts/api-server/src/routes/media.ts`, `customers.ts`

**Problem:** `PATCH /api/admin/media/:id` and `PATCH /api/admin/customers/:id` cast `req.body` fields directly with `as { ... }` without any Zod validation. Malformed or unexpected input goes straight to the DB update.

**Fix:**
```typescript
// In media.ts PATCH handler
import { z } from 'zod';

const patchMediaSchema = z.object({
  title: z.string().optional(),
  category: z.string().optional(),
  tags: z.array(z.string()).optional()
});

const body = patchMediaSchema.parse(req.body); // throws ZodError on invalid input

// In customers.ts PATCH handler
const patchCustomerSchema = z.object({
  marketingNotes: z.string().optional(),
  tags: z.string().optional()
});

const body = patchCustomerSchema.parse(req.body);
```

### 11. Base64 images stored in PostgreSQL

**File:** `lib/db/src/schema/media.ts`, `artifacts/api-server/src/routes/media.ts`

**Problem:** `media_items.image_data` stores the full base64-encoded image directly in a PostgreSQL text column. Every `GET /api/admin/media` loads all images from the database. As the media library grows, this will cause slow queries, bloated DB backups, and high memory usage.

**Recommended fix:** Migrate to object storage (Cloudflare R2 is free up to 10GB and integrates easily). Store only the public URL in the database.

```
1. Create a Cloudflare R2 bucket
2. On upload: PUT the binary to R2, store the returned URL in image_data
3. On GET: return the URL (no change to API shape, just the value changes)
4. Migrate existing records: decode base64 → upload to R2 → update DB row
```

### 12. No pagination on list endpoints

**File:** All `GET` list routes in `artifacts/api-server/src/routes/`

**Problem:** All list endpoints return every row. Fine now, but at 500+ bookings this becomes noticeably slow.

**Fix:**
```typescript
// Add to each list handler
const page = parseInt(req.query.page as string) || 1;
const limit = parseInt(req.query.limit as string) || 50;
const offset = (page - 1) * limit;

const results = await db.select().from(bookings)
  .orderBy(desc(bookings.createdAt))
  .limit(limit)
  .offset(offset);

const total = await db.select({ count: sql`count(*)` }).from(bookings);
res.setHeader('X-Total-Count', total[0].count);
res.json(results);
```

### 16. No CSV export for bookings or quotes

**Problem:** The admin has no way to export data for accounting or reporting. This is a common need for any service business.

**Fix:**
```typescript
// Add to bookings.ts
router.get('/bookings/export', requireAdmin, async (req, res) => {
  const rows = await db.select().from(bookings).orderBy(desc(bookings.createdAt));
  const csv = [
    'ID,Name,Email,Phone,Service,Suburb,Date,Status,Created',
    ...rows.map(r => `${r.id},"${r.customerName}","${r.customerEmail}","${r.customerPhone ?? ''}","${r.serviceType}","${r.suburb}","${r.preferredDate}","${r.status}","${r.createdAt}"`)

  res.setHeader('Content-Type', 'text/csv');
  res.setHeader('Content-Disposition', 'attachment; filename="bookings.csv"');
  res.send(csv);
});
```

## ✨ Feature Suggestions

---

### F1. Wire up the voice chat (already installed, not connected)

`@workspace/integrations-openai-ai-react` ships `useVoiceRecorder`, `useAudioPlayback`, and `useVoiceStream` hooks that are installed but not connected to any UI. Adding a mic button to `ChatWidget.tsx` would enable voice-to-text input with almost no backend work. This is a half-day job that would make the AI assistant genuinely stand out.

---

### F2. Automated booking reminder SMS

Once a booking is confirmed with a date, no automated reminder is sent. A 24-hour-before reminder via Twilio would reduce no-shows. Could be implemented as a simple cron job that queries confirmed bookings due tomorrow.

---

### F3. PDF quote/invoice generation

The admin can manage quotes but cannot generate a PDF to send to a customer. A downloadable PDF quote (using a library like `pdf-lib` or `puppeteer`) would make the workflow end-to-end without the need for a separate invoicing tool.

---

### F4. Funnel analytics: quote → booking → completed conversion

The dashboard shows raw counts (total bookings, pending quotes) but no conversion rates. The most actionable metric for a service business is: what percentage of quotes become bookings, and what percentage of bookings complete? Adding this to the analytics endpoint and dashboard would give real business insight.

---

### F5. SEO — LocalBusiness structured data (JSON-LD)

The site has no JSON-LD structured data. Adding a `LocalBusiness` schema with the ABN, REC number, service areas, phone, and email in `index.html` would significantly improve local Google search visibility for Mornington Peninsula and surrounding area searches.

```html
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "LocalBusiness",
  "name": "Electrical Installers",
  "telephone": "0419 868 703",
  "email": "info@electricalinstallers.com.au",
  "areaServed": ["Mornington Peninsula", "St Kilda", "Warragul"],
  "identifier": "REC 25510",
  "vatID": "35 608 171 802"
}
</script>
```

---

### F6. Customer booking status page (no login required)

Customers currently have no way to check their booking status after submitting. A simple status page accessible via a unique token link (sent in the confirmation email) would reduce inbound phone enquiries without needing full customer accounts.

---

### F7. Bulk SMS/email to customer segment

The Customers CRM collects tags and marketing notes but has no way to act on them. A "send SMS to all customers tagged X" feature would turn the CRM from a read-only table into a real marketing tool. This already has Twilio and Nodemailer wired up — it's mostly a UI and endpoint addition.

---

### F8. Google Reviews prompt in confirmation emails

The booking confirmation email to customers is a high-engagement moment. Adding a line like "Happy with the job? Leave us a Google review: [link]" at the bottom would build the Google Business Profile ranking at zero extra cost.
